Setting Up The Assistant

Keywords: assistant, setup, astra ai, astra-ai, model, gguf, llama.cpp, llama-server, build, whisper, voice, espeak, start, stop, journal, skills, avx

The assistant is two pieces and neither is bundled: a model file and the llama.cpp

runtime. astra ai setup is the guided starting point - it creates the two directories

the package expects (~/.local/share/astraos/ai/models and ~/.local/share/astraos/ai/bin),

reports what is already there, and tells you which of the two is missing. If you already

have a GGUF file, import it yourself with astra ai setup ~/path/model.gguf, which

copies it into the model directory - this is the whole download-free path, and nothing

is fetched at any point.

To fetch a model instead, use the package's own catalogue: astra-ai setup --list shows

it, and astra-ai setup --model NAME downloads one entry. Copy the names exactly from

that list, because a name that is not in it fails with unknown model.

There are two tiers to install, on purpose, and the order matters:

spark-x2.5-1.7b-q4_k_m is the executor, about 1.0 GB. It is the one that is always

needed: it reads a request, runs one action, verifies what happened and reports back.

smollm3-3b-q4_k_m (about 1.8 GB) is the alternative executor, a different model family,

if you would rather carry a 3B.

spark-x2.5-4b-q4_k_m is the middle brain, about 2.4 GB, and it needs 6 GB

of RAM or more. It is the one that plans multi-step work, and installing it is what turns

the assistant from a one-command tool into something that can do a task. The two are

separate commands because loading both at once on a machine with 4 GB is the difference

between an assistant and a machine that swaps your desktop out - the assistant loads one

model at a time, and a plan costs a reload of about ten to thirty seconds.

For machines that cannot afford those, the catalogue has smaller alternatives:

qwen2.5-1.5b-instruct-q4_k_m (about 1.1 GB) as the executor and

qwen2.5-3b-instruct-q4_k_m (about 1.9 GB) as a middle brain for 4 GB.

If you have fine-tuned a model yourself, or downloaded a GGUF from somewhere else, import

the file directly with astra ai setup ~/path/to/your.gguf and no download happens at

all. That is the supported path for a custom model, and it is the one a fine-tuned model

should take.

The runtime is the llama-server binary, on PATH or in the assistant's own bin

directory. astra-ai setup --build llama builds it from upstream source, and there is a

real reason to prefer that over downloading a release binary: on this class of CPU - AVX

but no AVX2, no F16C, no FMA, no BMI2 - a prebuilt binary dies immediately with an illegal

instruction, and the build only takes a few minutes.

The build has one variant per CPU class, chosen with --variant:

  • avx (the default) turns AVX on and AVX2, F16C, FMA and BMI2 off - the Sandy Bridge

this release is tested on has exactly AVX. FMA and BMI2 matter as much as AVX2: they

are Haswell features and the build enables them by default even with AVX2 switched

off, which produced a server that died with SIGILL and no output at all on the first

model it loaded.

  • avx2 turns AVX2, F16C, FMA and BMI2 on - most of ggml's speed on Haswell and later.
  • auto picks the newest variant this machine's CPU can run, read from /proc/cpuinfo.

Both variants pass -DGGML_NATIVE=OFF -DGGML_AVX512=OFF -DGGML_BLAS=OFF -DBUILD_SHARED_LIBS=OFF: never the build machine's own instruction set, no AVX-512, and

one self-contained installed file instead of an executable that still needs the build

tree for its libraries. A named variant is checked against /proc/cpuinfo before the

first compiler runs - --variant avx2 on a machine without AVX2 is refused with that

reason, because the resulting binary would die with SIGILL on the first question - and

the choice is recorded beside the installed binaries, which astra-ai status checks

against the CPU. The same applies to whisper with astra-ai setup --build whisper (or

--build all for both).

There is a third way that skips the compiler without risking the wrong CPU: AstraOS's own

CI builds both programs for both variants (the Build AI engine workflow) and publishes

each as a workflow artifact together with SHA256SUMS.txt and BUILD-INFO.txt:

astra-ai-engine-linux-x86_64-avx runs on Sandy Bridge and later,

astra-ai-engine-linux-x86_64-avx2 needs Haswell or later. Download the artifact whose

name matches the machine, copy llama-server and whisper-cli into

~/.local/share/astraos/ai/bin/, and astra-ai status shows the path it found. A binary

downloaded from anywhere else is still the thing to avoid: nobody there built it for this

CPU.

Voice needs one more thing: astra-ai setup --voice covers espeak-ng for speaking and a

whisper model for transcribing, and astra ai say TEXT speaks a line through the

machine's own speakers.

Once a model is ready, astra ai start serves the page at http://127.0.0.1:8765/ and

astra ai open opens it in the browser; astra ai stop stops it, and Ctrl+C in the

terminal also does. astra ai status answers "is it running, is a model installed" at

any time. astra ai start --lan makes the same page reachable from other devices on the

local network, which prints a warning line for a reason: there is no password and no TLS,

so anyone on that network can open the page and chat, though actions still require a

confirmation in the page they are watching. Use it on a network you trust, for the

minutes you need it, and stop the server afterwards.

astra ai with no subcommand prints the list it supports. astra ai journal shows what

the assistant has done - the tasks, the steps, the commands that ran - and astra ai skills lists the skill files installed, both the ones AstraOS ships under

/usr/share/astraos/ai/skills/ and your own in

~/.local/share/astraos/ai/skills/; a skill in your own directory wins over the shipped

one of the same name. astra-ai actions prints the fixed list of things the assistant

may do, and astra-ai ask QUESTION asks a single question without the page. Both are

worth reading: the action list is the complete repertoire, and it contains nothing that

installs, upgrades or sends anything, because all of that would need root.

Fixing Common Boot And Graphics Problems

Keywords: desktop, panel missing, stock desktop, no sound, pipewire, pavucontrol, brightness, backlight, video group, virtualbox, guest additions, resolution, xrandr, x11, wayland, graphics, xorg

The desktop looks like plain Xfce - no AstraOS panel, no wallpaper, no theme. The

AstraOS panel, wallpaper, keyboard shortcuts and theme are seeded from /etc/skel into

a home directory when the account is created, so a fresh install has them and an account

that already existed on the machine does not. The other half of it is that Xfce reads

those defaults only at the first login of a new account; after that, whatever is in

~/.config/xfce4/xfconf/xfce-perchannel-xml/ wins. So log out and back in first - that

alone is the fix most of the time. If the panel is still missing, the panel's own channel

file has gone invalid and Xfce has regenerated a default; move it aside with

mv ~/.config/xfce4/xfconf/xfce-perchannel-xml/xfce4-panel.xml ~/ and log out and back

in again, and Xfce rebuilds one. That mv is yours to run, and it is worth knowing what

it costs: any panel item you had added by hand goes with it and has to be added back.

No sound. AstraOS uses PipeWire, not PulseAudio directly - the image installs

pipewire, pipewire-alsa, pipewire-pulse and pavucontrol. Check the user services

first: systemctl --user status pipewire wireplumber. If either is not running,

systemctl --user restart pipewire wireplumber brings them back, and no root is needed

for any of it. Then open pavucontrol and look at two things: which output device is

selected, and whether the application you expect to hear is not muted in its stream. A

muted channel is the most common cause of all, which is what alsamixer -c 0 is for -

m toggles mute, and a column showing MM is muted. In a virtual machine, check that

the machine has an audio controller at all, because a VM with no sound hardware

configured produces exactly this symptom with nothing wrong in the guest.

Brightness. The kernel exposes the backlight at

/sys/class/backlight/<device>/brightness, and writing to it is a root-owned operation

unless a udev rule grants your account access - which on Debian it does for members of

the video group. If the brightness keys do nothing and a tool reports that it cannot

change the backlight, check groups: if video is not listed, the fix is

sudo usermod -aG video $USER followed by logging out and back in. None of

brightnessctl or light is installed by default, so astra install brightnessctl is

the other half of the answer, and it is one you type. Under X11 there is also

xrandr --brightness 0.8, which dims the whole screen in software rather than lowering

the backlight - useful on a desktop, powerless to save battery, and gone on logout.

VirtualBox: no clipboard, no shared folders, wrong resolution. The VirtualBox Guest

Additions are deliberately not part of the image; that is why copy and paste between

host and guest does not work out of the box. In the VirtualBox window, Devices, Insert

Guest Additions CD image, then run the installer from the mounted CD - it needs root, so

it is your command to type. After a reboot, xrandr lists the virtual outputs, and

resizing the VirtualBox window (or View, Virtual Screen 1, then a resolution) is honoured

because the additions provide the driver. While you are in the machine's Display

settings, VMSVGA is the graphics controller to choose for a Linux guest, and give it as

much video memory as the dialog allows; the older VBoxVGA and VBoxSVGA choices are what

produce a stuck low resolution.

Wayland or X11. AstraOS's desktop is Xfce on X11 in this release; the graphics list

is X11 only and the documentation says so, so a program that requires Wayland is not

going to run, and an X11 program runs everywhere. If someone tells you to switch the

session to Wayland, that is future work, not an option in front of you - and if the

graphics fail outright, the failsafe entry in the GRUB menu is the supported first step,

because it disables kernel modesetting and the ACPI workarounds.

Where to look when the graphics fail at boot. astraos-recovery-guide prints the

recovery steps for login loops, no boot and broken updates, and it is installed. For a

graphics fault specifically, the X server's own log is more specific than the journal;

it is written by the session at ~/.local/share/xorg/Xorg.0.log on this system, since X

runs as your user rather than as root. systemctl --failed and

journalctl -b -p err cover the rest, and every one of those commands is read-only.

Installing Extra Software On AstraOS

Keywords: install, software, package, apt, astra install, synaptic, flatpak, program, application, new app, apt-get, pip

Software on AstraOS is Debian software, and there is one front door to it: astra install NAME, which is a wrapper around apt-get install --assume-yes NAME and will ask for

your password because installing a package changes system files. Its companions are

astra search NAME (a search of the Debian archive, via apt-cache search), astra update (apt-get update, which refreshes the package lists), astra remove NAME

(removes a package, after asking), astra apps (what is installed) and astra repair

(dpkg --configure -a and apt-get install --fix-broken, for a broken package database).

apt-get itself works if you prefer it; astra just spares you typing the common forms

and refuses to guess.

The graphical front end is Synaptic, which is already installed and does the same thing

with a list: search for a package, mark it for installation, apply. The Welcome

application that opens on a fresh system points at both, lists what is already here, and

offers no downloads of its own. Between them they cover the case that matters - a package

that exists in Debian trixie, installed with its dependencies sorted out by apt.

Flatpak is not installed, and this is stated plainly rather than dressed up. The image

deliberately ships no Flatpak and no PackageKit daemon; the reason is that a distribution

this size does not need two competing package systems, and Synaptic plus apt already

cover Debian's archive. The flatpak package does exist in Debian trixie and

sudo apt-get install flatpak would install it, but nothing in this release is set up

for it: no Flathub remote is configured and no application in the image is built as a

Flatpak. Treat Flatpak as something you can add, not something that is supported here,

and expect to configure the remote yourself.

The assistant will not install anything. Its whole action list is in

/usr/lib/astraos/ai/actions.py and contains no install, no upgrade and no package

action; the one action that can run a command refuses sudo, pkexec, su and doas

before the command is even executed. So when you ask it to install something it will

answer with the command - astra install <name> - and let you run it, because the

assistant runs as your user account with no password and no root, exactly like any other

program you start. This is not a missing feature; it is the boundary that keeps an

assistant from changing your system without a human in front of it.

Two things you can do without root. Programs that ship as a single executable can be

unpacked into ~/.local/bin and run from there - ~/.local/bin is on the default PATH

on Debian for your own account - and Python libraries can be installed into a virtual

environment with python3 -m venv ~/venv && ~/venv/bin/pip install <name>. The venv

matters because Debian trixie marks the system Python as externally managed, so a plain

pip install into it fails with an "externally-managed-environment" error. Anything that

needs /usr changed is apt's business and therefore yours.

Keyboard Shortcuts On AstraOS

Keywords: keyboard, shortcuts, keys, super key, windows key, hotkeys, keybindings, xfce4-keyboard-shortcuts, whiskermenu, lock screen, screenshot key, setxkbmap

The keys that come from Windows work here. AstraOS binds Super+E to open the file

manager (Thunar), Super+R to open the run launcher (xfce4-appfinder, the box where

you type a command name), Super+T to open a terminal (xfce4-terminal), and Super+L

to lock the session (xflock4, the same lock Windows uses). The Super key is the one

with the Windows logo on it. Super+S opens the Start menu rather than taking a

screenshot, and Super+D shows the desktop. The screenshot keys are Print for the

whole screen and Shift+Print for a region, both of which run xfce4-screenshooter; if

you come from Windows expecting Super+S to capture, the one to press is Print.

The rest of the desktop keeps the conventional Xfce and Windows bindings, so nothing has

to be relearned: Ctrl+Alt+T opens a terminal, Ctrl+Alt+H the file manager,

Ctrl+Alt+F Firefox, Ctrl+Alt+W the Start menu, Ctrl+Alt+I an AstraOS information

window, and Ctrl+Alt+Delete logs out. Ctrl+Shift+Escape opens the task manager, which

is worth remembering when the desktop freezes. Windows and workspaces stay on the

familiar ones - Alt+F4 closes, Alt+F10 maximises, Super+Left and Super+Right tile

a window to one side, Super+Up maximises, and Ctrl+Alt+Left / Ctrl+Alt+Right switch

workspace.

These bindings live in the xfce4-keyboard-shortcuts channel of Xfconf, which on this

machine is the file

~/.config/xfce4/xfconf/xfce-perchannel-xml/xfce4-keyboard-shortcuts.xml. It is plain

XML, one <property> per key, and it is copied into the home directory from /etc/skel

when the account is created - which is why a fresh install gets the AstraOS keys and an

account that already existed on the machine does not. The distribution cannot ship the

same file under /etc/xdg/xfce4/xfconf/xfce-perchannel-xml/ because Debian's Xfce

packages own that path and dpkg refuses a second owner.

To change one, use Settings, then Keyboard, then Application Shortcuts: double-click the

binding you want, press the new key combination, and it takes effect immediately. There

is no need to log out first for a change made in the GUI. Editing the XML by hand also

works, but only after logging out and back in, because the running Xfce configuration

daemon holds the values in memory - hand-editing a file the daemon has already read is

the usual reason "I changed the shortcut and nothing happened".

Two things follow from how Xfce works. First, once anything is changed in the settings

editor, Xfce writes its own complete copy of the channel, and that copy wins over the

skeleton default; the AstraOS bindings that were not touched stay in it, unchanged.

Second, a binding that the keyboard cannot produce simply never fires, which is harmless

  • a key combination assigned to a program that is not installed does the same.

The Time Zone And The Locale

Keywords: timezone, time zone, clock, wrong time, timedatectl, set-timezone, locale, language, tzdata, ntp, keyboard layout, setxkbmap

timedatectl with no arguments is the whole diagnosis, and it needs no root: it prints

Local time, Universal time, the Time zone currently in force, whether the system

clock is synchronised, and whether the NTP service is active. A right clock in the wrong

zone is a timezone problem; a wrong clock with the right zone is a sync problem, and the

same output distinguishes them. To see every valid zone name run timedatectl list-timezones, which prints several hundred lines of the form Continent/City.

Setting the zone is one command, and it needs root: sudo timedatectl set-timezone Europe/London, with the zone name copied exactly from the list. What it changes is

/etc/localtime, a symlink into /usr/share/zoneinfo that is owned by root, so the

machine asks for your password - correctly, because a wrong zone breaks TLS certificate

checks and log ordering as surely as it breaks the clock in the panel. On a systemd

system this is preferred to the older sudo dpkg-reconfigure tzdata, which still works

and rewrites the same file. Time sync is the same shape: sudo timedatectl set-ntp true

turns on systemd-timesyncd, the one synchronisation daemon AstraOS enables - the image

ships no chrony, ntpsec or openntpd, and those packages declare a conflict against the

systemd one anyway, so installing a second one is a downgrade rather than an upgrade.

The assistant prints these commands and does not run them. It runs as your user account,

it has no password, and its command runner refuses sudo, pkexec, su and doas

outright; timedatectl set-timezone typed without sudo would simply fail with a

permission error. If you ask it to fix the time it will tell you which of the two

problems you have and the exact line to paste into a terminal.

If the clock is wrong by a whole number of hours after the machine has been off, and the

timezone is correct, check whether anything else on the disk uses local time: the usual

cause is a second operating system that sets the hardware clock to local time, where

Debian expects it in UTC. The timezone files cannot repair that disagreement; the fix is

a setting on the other system, not on this one.

The locale is the same story in a different file. locale shows what your session is

using, localectl status shows what the system is set to, and /etc/default/locale

holds the answer for every login - read it with cat /etc/default/locale. To change it,

first make sure the locale exists (sudo dpkg-reconfigure locales generates it), then

set it with sudo update-locale LANG=en_GB.UTF-8, again a root-owned system file. The

keyboard layout that turns what you type into the right characters is checked with

setxkbmap -query and is changed in Settings, Keyboard, Layout - a change made there

survives a logout, while setxkbmap gb typed in a terminal only lasts until you log out.

What The Assistant Sends, And What It Does Not

Keywords: privacy, network, upload, telemetry, offline, local, 127.0.0.1, lan mode, password, search_web, whisper, espeak, journal, what leaves the machine

The assistant runs on this computer. It binds to 127.0.0.1:8765 - localhost only - so

nothing outside the machine can reach it, and the model inference happens on the local

CPU through llama.cpp. The web page it serves is one HTML file with its styles and script

inline: it makes no request of any kind except to the server that served it, and there are

no fonts, scripts, trackers or analytics endpoints in it to fetch. That is a property the

distribution checks, and the page would not work on a machine with no internet

connection anyway. There is no telemetry, no crash reporting, no account, no cloud

provider and no API key to configure; there is no configuration in which the assistant

talks to a server belonging to AstraOS, because there is no such server.

Two things do leave the machine, and both are decisions you make rather than defaults you

inherit. The first is astra ai start --lan: it opens the same page to every device on

the local network, with no password and no TLS, so anyone who can reach your address can

read the conversation and ask questions. Actions still require a confirmation in the page

that is watching, so a stranger can propose but the person at the PC decides - and that is

the whole of the protection, which is why the server prints its warning line at startup and

why the right way to think about --lan is "a room I have unlocked for ten minutes", not

"a feature I have turned on". The second is search_web: that action hands the query to

your browser, where a web search obviously goes to the internet. It is deliberate - there

is no search in the action repertoire that reports results without doing that - and if you

asked the assistant something and it opened a browser, that request left the machine.

Voice is local, with one caveat worth knowing. Speech synthesis uses espeak-ng (or

spd-say) on this machine, and speech recognition through whisper.cpp runs on this

machine too: a recording made in the page is posted to 127.0.0.1 and transcribed there,

so the audio goes nowhere else. Where the browser offers its own speech recognition, the

page asks for on-device transcription; some browsers instead route audio to their vendor's

service, which is a browser behaviour outside AstraOS's control, and it is why the page's

promise is about its own requests and not about everything the browser does. If that

matters to you, use the recorded-audio path.

What the assistant writes down is also on this machine and never uploaded. Its journal

lives in ~/.local/share/astraos/ai/journal.sqlite3, and it records the tasks it was

given, the steps it took and the commands it ran, so astra ai journal can answer "what

did you do" afterwards. Conversations are not persisted: a reload forgets the transcript,

which lived in the page's memory and in the model's context window and nowhere else. The

skills and knowledge it quotes are plain files under /usr/share/astraos/ai/ and your own

under ~/.local/share/astraos/ai/.

The honest boundary of all of this: the assistant runs as your user, with your rights and

no others. The model server is the one part that can be caged - with bubblewrap or

firejail installed, llama-server runs with the root and the model folder read-only and

private /tmp and /dev/shm - but the actions themselves have no AppArmor profile and no

container, and the server keeps the host network so the page can reach it over

127.0.0.1. It can read your files and run commands in your name, which is exactly what

makes it useful and exactly why the action repertoire is a short fixed list, why anything

destructive waits for a confirmation in front of you, and why it refuses to run anything

as root. A setup step like astra-ai setup --model NAME does fetch a model from a third

party - that is a request to a server somewhere else, made by you, to get a file - but the

assistant's own operation never sends anything.

Setting DNS on AstraOS

Keywords: dns, resolv.conf, nameserver, networkmanager, nmcli, resolvectl, systemd-resolved, resolvconf, no internet, name resolution, dns boot parameter

On AstraOS the DNS settings come from NetworkManager and from nothing else. The image

ships network-manager, network-manager-gnome, modemmanager and wpasupplicant,

and the build deliberately ships no resolvconf package, because the two defer to

each other and leave /etc/resolv.conf unwritten. NetworkManager writes

/etc/resolv.conf itself, which is the Debian 13 way; resolvconf is deprecated

upstream and is not installed here. Start with nmcli device status: a device that is

connected, with a connection listed by nmcli connection show --active, means

NetworkManager believes it has a working path, and the question is only what it was told

to put in resolv.conf.

/etc/resolv.conf may be a symlink, and that is the first thing to check: ls -l /etc/resolv.conf. On a machine where systemd-resolved is running it points at

/run/systemd/resolve/stub-resolv.conf (which contains the line nameserver 127.0.0.53),

and resolvectl status is the tool that shows which DNS servers resolved actually knows

about per interface. Where NetworkManager writes the file directly it is a regular file

holding one nameserver line per server, usually filled in from the router by DHCP.

Either arrangement is correct. What is not correct is editing the file by hand:

NetworkManager rewrites it every time a connection comes up, so a hand-typed nameserver

survives until the next reconnect and then vanishes with no error explaining why.

To set a DNS server that sticks, change the NetworkManager connection rather than the

file. nmcli connection show lists the connections by name; then

nmcli connection modify "Wired connection 1" ipv4.dns "10.0.2.3 8.8.8.8" ipv4.ignore-auto-dns yes

followed by nmcli connection up "Wired connection 1" sets the servers you chose and

stops the router's DHCP answer from adding its own. The same edits work in the desktop:

the network icon, then Wired or Wi-Fi settings, has the DNS field per connection. Both

routes write into /etc/NetworkManager/system-connections/, which is a root-owned system

file, so the machine will ask for the user's password. This assistant cannot do it - it

runs as the user, never as root, and refuses sudo before it is even executed.

The failure looks like this: ping 1.1.1.1 answers and ping debian.org answers

Temporary failure in name resolution, and every browser says it cannot find the server

while the network icon shows a normal connection. That is a DNS fault with a working

link, not a broken network. Confirm with getent hosts debian.org, which asks the

resolver and nothing else. AstraOS 0.1.0 had a specific version of this fault in the live

session: /etc/resolv.conf was a zero-byte regular file because live-build replaced

the path instead of leaving the /run/resolvconf/resolv.conf symlink, and both

NetworkManager.service and resolvconf.service were enabled and each deferred to the

other, so nothing wrote it. The fix was removing resolvconf from the image, and it

should not be installed again. The workaround that was documented for that live session

echo "nameserver 10.0.2.3" | sudo tee /etc/resolv.conf was a temporary measure that

was lost on reboot, and on a system where NetworkManager owns the file it is lost on the

next reconnect.

One AstraOS-specific override sits above all of this: a live medium booted with the

dns= boot parameter. live-boot reads that parameter at boot and writes the given

nameserver into /etc/resolv.conf, which supersedes whatever NetworkManager or DHCP

would have configured, and it stays until the next boot. If the live session resolves

through a server that is not the router's, look at the kernel command line first - in the

GRUB menu, select the entry, press e, and check for dns= on the linux line. Remove

the parameter (or change the address) to let NetworkManager do its job; it is a boot

entry, not a file to edit.

Back Up And Sync Files With Rsync

Use this when: the user wants files copied to an external drive, wants a backup made, or wants two folders kept the same
Keywords: backup, back up, rsync, copy, sync, external drive, restore, checksum, verify, documents, pictures, archive

---

Steps

  1. Ask where the backup goes, if it is not already known - a path on an external drive under /media/<you>/<label>/, or a folder in the home directory. Do not pick a destination yourself.
  2. Check the destination has room: run_command df -h /media/<you>/<label> and compare the Avail column with what run_command du -sh ~/Documents reports for the source. A backup that does not fit is not a backup.
  3. Confirm the destination exists and note what is already in it: run_command ls -la /media/<you>/<label>. If the target folder inside it does not exist yet, it is created in step 6, not now.
  4. Do the dry run: run_command rsync -av --dry-run ~/Documents/ /media/<you>/<label>/astraos-backup/Documents/. The trailing slash on the source means "the contents of this folder"; without it rsync would copy the folder itself into the destination, one level deeper than the user asked for.
  5. Read the dry run. --dry-run changes nothing: it prints every file that would be copied, every directory that would be created, and a final line giving the total size. Report that list and that total.
  6. Create the destination folder once, only if the dry run said it would be created: run_command mkdir -p /media/<you>/<label>/astraos-backup/Documents.
  7. Stop and let the user decide. Print the dry run's full list, then SHOW THE LIST AND WAIT FOR CONFIRMATION. The user has to say yes to that list before a single byte is copied. A hesitating answer, or no answer, is a no.
  8. Only after a yes, run the real copy, the same command with --dry-run removed: run_command rsync -av ~/Documents/ /media/<you>/<label>/astraos-backup/Documents/. One rsync per directory - repeat for ~/Pictures/ and ~/.config/ as separate commands, so each output stays readable and each can be checked.
  9. Verify the copy: run_command rsync -av --checksum --dry-run ~/Documents/ /media/<you>/<label>/astraos-backup/Documents/. --checksum compares file contents instead of timestamps. If this second pass prints no file names, the destination matches the source exactly. Report that, and report anything it lists.
  10. If the user asked to make the destination match the source exactly - deleting files in the destination that no longer exist in the source - run the dry run with --delete added first, print what it would remove, and SHOW THE LIST AND WAIT FOR CONFIRMATION before running the real thing. A --delete nobody was shown is data loss with no witnesses.

Notes

-a is archive: it preserves times, permissions, symlinks and recursion, which is what "the same files" means. -v is verbose, and it is what makes the dry run's output the list you show. --dry-run is the whole safety model of this skill - rsync is fast and destructive at the same time, so the plan always runs first and the copy never runs unannounced.

The source is never modified. Rsync reads ~/Documents, ~/Pictures and ~/.config and writes only to the destination. --delete is the one flag that changes that relationship, because it acts on the destination; that is exactly why it needs its own confirmation with its own list.

~/.config is a hidden directory and holds the desktop settings - keyboard shortcuts, panel layout, the assistant's settings. Include it when the user asked for a full backup, but never --delete a .config backup without the list, because the destination may be a machine whose desktop is configured differently.

Nothing here deletes a source file, truncates a source file, or writes outside the destination. If a step looks like it rewrites something in ~, it is wrong - re-read step 4.

Find And Organise Files

Use this when: the user cannot find a file, wants a folder tidied, or wants files moved somewhere else
Keywords: find, files, search, locate, organise, organize, tidy, move, disk, downloads, clean up, extension, old files, large files

---

Steps

  1. Search by name, case-insensitively: run_command find ~/Documents -iname "*report*" -type f. -iname matches either case; -type f keeps it to files and skips directories.
  2. Search by extension: run_command find ~/Downloads -type f -name "*.pdf". One extension per command.
  3. Search by age: run_command find ~/Downloads -type f -mtime +30 finds files last modified more than 30 days ago. Change the number, not the flag.
  4. Search by size: run_command find ~/Downloads -type f -size +100M finds files over 100 megabytes. +100M means "more than"; without the leading + it means exactly that size and finds nothing useful.
  5. Inspect what you found, one command at a time: ls -la ~/Downloads/<file> for the size, the date and the permissions; du -sh ~/Downloads for how much space the whole folder takes; file ~/Downloads/<file> for what the file actually is, which is how you tell a PDF renamed to .txt.
  6. Build the plan in words before touching anything. For every file, print one line of the form ~/Downloads/old-thing.pdf -> ~/Documents/reports/. Finish with the count of files and the total size, from du -sh.
  7. Show the plan and stop. Print the complete list in the answer, exactly as it will be executed, then SHOW THE LIST AND WAIT FOR CONFIRMATION. The user has to say yes to that list. Silence, a change of subject, or "probably fine" is not a yes.
  8. Only after the user confirms: run_command mkdir -p ~/Documents/reports once, if the destination folder does not exist yet.
  9. Then move, one directory at a time so the output stays readable: run_command mv ~/Downloads/old-thing.pdf ~/Documents/reports/. mv keeps the file's contents and timestamps and removes it from where it was, so a move is also the last moment it is easy to undo. Only a list the user has already said yes to may be moved - SHOW THE LIST AND WAIT FOR CONFIRMATION for any list that was not printed and agreed, including a single file.
  10. Verify the move: run_command ls -la ~/Documents/reports/ and confirm every file on the list arrived. Report anything that did not.

Notes

The list is the safety mechanism, and printing it is a real step rather than a courtesy. A user who is shown ten files and asks you to move them has told you what they wanted; a user shown "moved your downloads" afterwards has not been told anything they can check.

Never use find -delete. It removes files as it walks, it has no undo, and its -name pattern matches far more than people expect - an empty quotes result deletes nothing and a stray dot deletes the folder. Never use find -exec mv either: it moves files the moment it finds them, in whatever order the filesystem returns them, and the list never reaches the user's eyes before the damage. If a step appears to delete or move anything, it must first print the list and get a yes.

mv is the only move action available. There is no copy-and-delete trick worth doing: mv within one filesystem is a rename and does not rewrite the data, so it is both faster and safer than copying and removing the original.

One find command may only ever contain a search and an action that prints. Flags such as -print, -mtime and -size are fine. -delete, -exec, -execdir, -ok and -fprint are not, and this assistant's command runner refuses a ; anyway, which most -exec forms need.

Set The Locale And Timezone

Use this when: the clock or the date is wrong, the user wants a different timezone or language, or the keyboard types the wrong symbols
Keywords: locale, timezone, time zone, timedatectl, set-timezone, keyboard layout, setxkbmap, time, clock, language, tzdata, wrong time

---

Steps

  1. Report what is set now: run_command timedatectl. It prints Local time, Universal time, Time zone, System clock synchronized and whether the NTP service is active. This is the fact the whole task starts from, and it needs no root.
  2. List the valid zone names: run_command timedatectl list-timezones. It prints several hundred lines of the form Continent/City. If the user named a city, ask them to pick the exact line from that output - never assume the spelling, because a wrong zone name silently sets the wrong time.
  3. Check the keyboard layout of this session: run_command setxkbmap -query. It prints the layout, variant, model and options X11 is actually using, which is the only way to know what the physical keys will produce.
  4. Apply a layout to the running session when asked: run_command setxkbmap gb for a British layout, setxkbmap us for a US one. This lasts until the user logs out, and it is the correct action for "the wrong symbols are coming out" right now. Making it permanent is the user's job in Settings, Keyboard, Layout.
  5. Read the system locale by asking the user to run cat /etc/default/locale in their own terminal, and read back what it prints. The assistant does not read or write anything under /etc, /boot, /usr or /var: its command runner refuses those paths on purpose, and this is the step where that rule shows up.
  6. Get the rest of the locale picture: run_command localectl status, which reports the system locale, the console keymap and the X11 layout as systemd sees them.
  7. Setting the time zone needs root, so STOP. Do not run sudo timedatectl set-timezone and do not run timedatectl set-timezone on its own - the first is refused by this assistant and the second fails with a permission error. Instead print the exact command for the user to run: sudo timedatectl set-timezone Europe/London, and say why it is theirs to type: it changes /etc/localtime, which is a system file, so it needs their password, and this assistant runs as their user with no password and no root.
  8. Give the same treatment to time sync: sudo timedatectl set-ntp true when the clock is drifting, and to the locale: sudo dpkg-reconfigure locales to generate the locale, then sudo update-locale LANG=en_GB.UTF-8 once it exists. Print them, explain them, and let the user run them.
  9. Close with a summary: what is set now, what should change, and the exact commands to change it, in order. Nothing was changed by the assistant.

Notes

This skill prints commands; it does not run anything that changes the system. That is not caution for its own sake - set-timezone, set-ntp, localectl set-locale and localectl set-keymap all write files owned by root, and a program running as the user cannot do them. The honest answer to "why won't you just do it" is one sentence: it needs your password, and I have no business having it.

A wrong clock with a right timezone is an NTP problem, not a timezone one; a right clock in the wrong zone is the opposite. timedatectl says which, in the same output, so step 1 settles the diagnosis before anything is proposed.

sudo dpkg-reconfigure tzdata is the older Debian way and still works, but timedatectl set-timezone is preferred on a systemd system and does not need the locale regenerated. The hardware clock is set from the system clock on shutdown by default on a normal Debian install, so changing the timezone is enough; there is no separate step for the RTC.

Triage Local Email Offline

Use this when: the user has local mail in a Maildir or an mbox file and wants it sorted, read, or a reply drafted
Keywords: email, mail, maildir, mbox, triage, inbox, reply, draft, offline, notmuch, message, unread, message headers

---

Steps

  1. Find the mail store. Ask the user if you do not know it. The usual places are ~/Maildir, ~/.local/share/mail, and a single ~/mail/archive.mbox file.
  2. Count what is there: run_command ls ~/Maildir/new for unseen messages and run_command ls ~/Maildir/cur for the rest. Note that a Maildir message is one file per message, named with a timestamp and flags.
  3. For an mbox file, count the messages with run_command grep -c "^From " ~/mail/archive.mbox. In an mbox every message starts with a line beginning From followed by a space, and that count is the number of messages.
  4. If notmuch is installed, use it instead and it is faster: run_command notmuch new to build notmuch's own index (it writes only that index, never a message), then run_command notmuch search tag:inbox for the list, then run_command notmuch show --format=text <id> for one message's headers and body. The last two are read-only.
  5. Read one message at a time: run_command cat ~/Maildir/new/<file>. Read the From, To, Subject and Date headers first, then the body. Do not read a message you have already read - each command costs a turn.
  6. Classify every message into exactly one of three groups: needs reply, needs reading, or can be ignored. Give the reason for each, in a phrase that names the file, for example needs reply - asks for the invoice number (Maildir/new/1750000000.M1P123.host).
  7. Print the three groups with their counts, the newest first. A message that goes in "can be ignored" still gets named - the user checks a classification by seeing what was in it.
  8. Draft the replies. Write each draft in the answer as plain text, with its own To, Subject and body, ready for the user to copy. Address it to the From header of the message it answers and keep the Subject as Re: <original subject>.
  9. Stop there. The drafts are printed for a human to read and send. Nothing is sent, marked as read, moved, filed or deleted, and no step exists that would do any of that.

Notes

The assistant cannot send email. There is no send action in the action catalog, no mail transport agent is configured by this distribution, and a step that says "send", "reply", "file" or "mark as read" as an instruction to the machine is wrong - those words only ever describe what the draft is for. The user sends from their own mail program with their own account.

This is an offline skill by definition: it reads files under the user's home directory and makes no network request of any kind. Do not open a browser, do not call search_web, and do not offer to "check the mailbox online".

Reading is the safe part, so be liberal with it. grep and cat on a mail file cannot change it. If a message is base64 or quoted-printable encoded, say so rather than printing the encoded block as if it were the text; grep -c "^From " remains the reliable count either way.

Reading And Converting A PDF

Use this when: the user wants the text out of a PDF, wants a document converted, or wants to know what is inside a file they cannot open
Keywords: pdf, pdftotext, extract, extraction, text, ocr, scanned, tesseract, convert, docx, soffice, poppler, document, pages

---

Steps

  1. Find the file and confirm it is really there: search_files with part of its name, then read_file if it is a text file. read_pdf names a missing file rather than returning an empty answer.
  2. Extract the text: read_pdf with the path. It runs pdftotext -layout with the output sent to standard output, which the action captures and returns.
  3. Read what came back. If it is a page or more of readable text, quote from it directly, name the file, and say how many pages it has if pdftotext printed page breaks.
  4. If the extraction comes back empty, or a handful of characters for a file that is clearly tens of pages, it is a scanned PDF: it has no text layer at all. read_pdf says so; repeat that rather than inventing contents.
  5. For a scanned page, render the first page to a PNG: run_command pdftoppm -r 300 -png -f 1 -l 1 ~/Documents/<file>.pdf /tmp/astra-page. One page at a time; a hundred pages at 300 dpi fills the disk.
  6. Run OCR on that image: run_command tesseract /tmp/astra-page-1.png stdout. The word stdout is the output file name and means "print it here" - it is not a mistake, do not replace it with a path.
  7. To convert a document the other way, use LibreOffice headless: run_command soffice --headless --convert-to docx --outdir ~/Documents ~/Documents/<file>.pdf. Replace docx with txt or pdf as asked. The --outdir directory must exist, and the input is never written to.
  8. Report the result: the file's name, how many pages it has, what it says, and - when you converted it - the exact path of the new file. Do not summarise a file you failed to read.

Notes

Extraction is read-only, every time. read_pdf reads a file from the user's folders and writes nothing; soffice --convert-to writes a new file in a directory the user named and leaves the original alone. If a step looks like it needs a writable copy of the input, that step is wrong - stop and re-read this one.

read_pdf reports a missing pdftotext with the package to install (poppler-utils). On AstraOS that package is installed; if it is genuinely missing, the answer is astra install poppler-utils, which the user must run because it needs root. tesseract (package tesseract-ocr, plus tesseract-ocr-eng for English) is not part of the image and is only needed for scanned pages; if it is missing, say OCR is unavailable and offer the rendered PNG instead.

Two flags that are worth knowing: -layout keeps the columns of a table roughly where they were, which is the difference between a readable document and one long line of mush; -f 1 -l 1 on pdftoppm is the page range, first and last. There is no step here that renames, moves or deletes a PDF.

Screenshot And Describe The Screen

Use this when: the user wants a screenshot taken, asks what is on the screen, or asks what windows are open
Keywords: screenshot, screen, describe, windows, picture, image, capture, what is on my screen, see, look

---

Steps

  1. Take the picture with the screenshot action. It takes no arguments, captures the whole screen, saves a PNG under ~/Pictures/Screenshots/ and answers with the exact path it produced. Read that path - do not invent a file name.
  2. List what was on screen with the list_windows action. It returns one line per open window, each an id and a title. That list is what makes the description checkable rather than a guess at pixel shapes.
  3. Match the two: for each window in the list, say what it is in one line, and note which one is the largest or which is on top. A window whose title names a document names its document - use that.
  4. If the user asked about one specific window, bring it forward with the focus_window action and a few words of its title. Use this only when asked; focusing a window changes what the user is looking at.
  5. Never use close_window. It can lose unsaved work and it is the one action in this group that asks the user first, which means a step that closes a window to take a look inside it has already accepted that risk.
  6. Tell the user where the file is: the path from step 1, which is already inside ~/Pictures/Screenshots/. If they asked for it somewhere else, run_command mkdir -p ~/Pictures first, then move only the file the screenshot action just created with run_command mv ~/Pictures/Screenshots/<file>.png ~/Pictures/. Never overwrite a picture that was already there: if the destination would replace an existing file, say so and SHOW THE LIST AND WAIT FOR CONFIRMATION before running the mv.
  7. Give the description as prose: the windows, which had focus, the time on the clock if it is visible, and anything obviously wrong (a dialog box, an error, an empty window). Do not claim to read small text at 100 percent zoom unless it is legible in the image.
  8. Nothing is uploaded. There is no upload action, and a step that mentions a web address is wrong for this skill.

Notes

The screenshot action is full-screen only - there is no region capture and no way to choose a window. If the user asked for one window, say the image includes the whole screen and describe the part they meant.

Screenshots are taken by xfce4-screenshooter on AstraOS, with scrot and ImageMagick's import as fallbacks. If none of them is installed the action says so and names the package; the fix (astra install xfce4-screenshooter) is one the user runs, because installing needs root and this assistant does not have it.

Describe what is visible, not what should be. A window title is evidence; a description of a window that is not in the list_windows output is a guess, and a guess in a report about the user's own screen is easy to catch and hard to forgive.

Summarise A Folder Of Documents

Use this when: the user wants a short brief out of a folder of text documents, or wants to know what a set of files is about
Keywords: summarise, summarize, summary, brief, folder, documents, txt, md, csv, pdf, report, digest, sources, cite

---

Steps

  1. List the folder first: search_files with part of the name, or read_file on a folder listing only if the user gave the folder. Read the whole listing before reading any file, so the brief is about what is actually there and not about the two files you happened to open.
  2. Sort the files into kinds by extension: .txt and .md are readable with read_file; .csv needs the header line read first; .pdf needs read_pdf; anything else - .docx, .xlsx, images, archives - is not text and needs a conversion step from the pdf-office skill before it can be summarised.
  3. Read a plain text file: read_file with the path. It returns the whole file, refuses a binary, and refuses anything over 1 MB; for a long file ask for a narrower question rather than inventing the middle.
  4. Read a CSV's shape before its rows: read_file returns the header and the first records, which is enough to say what the columns are. Never quote a number from a CSV you have not read a row of.
  5. Extract a PDF: read_pdf with the path. If it comes back with no text layer, say that in the brief under a "could not read" line and move on. Do not guess what a scanned PDF says from its name.
  6. When asked to compare two files, use compare_files; it returns a unified diff, and an identical pair says so rather than producing an empty answer that reads like a failure.
  7. Write the brief with write_file only when the user asked for a file; it writes inside the assistant's workspace, not into the user's Documents. One short paragraph per document, in the order the user gave or alphabetically, and at the end of every claim put the file it came from, for example (~/Documents/notes.md). A sentence that cannot be traced to a file does not go in the brief.
  8. Before saving or presenting the brief, run verify_citations with the brief and the paths you read. Fix every citation it reports as unresolved, or remove the sentence; a failed check is not a footnote to ignore.
  9. Add a section headed "What is missing". Name the questions this folder does not answer, and name the file or the source that would answer them - a project with no budget file, a log with no error report, a date range that starts after the event.
  10. Finish with the totals: how many files were in the folder, how many were read, how many could not be read and why. If the user asked for a file, print the path write_file returned.

Notes

The citation rule is the whole point of this skill. Every sentence in the brief must be attributable to one file path that was actually read. A model that summarises a folder it did not open produces fluent fiction with file names in it, and the user has no way to catch it - so: if a file was not read, it is not summarised, and it is named in the "could not read" lines instead.

There is no step here that writes to, renames or moves any source document. read_file, read_pdf, compare_files and verify_citations are read-only by construction; write_file writes only inside the assistant's own workspace. A brief is also allowed to be short: three documents summarised honestly beats twelve paraphrased from their file names.

If the folder is large, say so and ask the user which files matter before reading all of them; reading everything is the safe default only when the folder is small enough that every file really was opened. Numbers must be copied, never rounded, inferred or estimated - and a figure that appears in two files with different values is a contradiction to report, not one to average.

System Health Report

Use this when: the user asks whether the machine is healthy, wants a system report, or says the computer is slow or misbehaving
Keywords: health, report, system, disk, memory, cpu, journalctl, errors, failed, network, diagnostics, slow, check, monitoring, read-only

---

Steps

  1. Get the machine's identity: run_command fastfetch. It prints the kernel, the CPU model, the memory, the uptime and the graphics in one screen. If it is not installed, run_command cat /proc/cpuinfo for the processor and run_command cat /proc/meminfo for memory, which is the same information from the kernel.
  2. Check the disks: run_command df -h. Read the Use% and the Mounted on columns. Note every filesystem above 80 percent by name.
  3. Check memory: run_command free -h. Report total, used, free and the swap line. Used plus free is the total; if used is nearly the total, the machine is out of RAM and swapping.
  4. Check the kernel's swapping behaviour: run_command sysctl vm.swappiness. A high number means the kernel moves memory to disk early, which is why a machine with free RAM can feel slow on spinning disks.
  5. Check for units that failed: run_command systemctl --failed. This needs no root, prints nothing when nothing failed, and a listed unit is the single most useful line in the report.
  6. Read this boot's errors: run_command journalctl -p 3 -xb --no-pager. -p 3 is priority err and worse, -b is this boot, -x adds the explanation text, --no-pager prints instead of opening a pager.
  7. Check the network: run_command ip -br addr for one line per interface and its address, then run_command ip route for the default route. An interface with no address is the whole problem more often than not.
  8. Write the report with five headings - Machine, Disk, Memory, Services and logs, Network - and put the three things worth acting on at the top, each with the command that produced the number.
  9. State plainly what you did not check and could not check. Do not fix anything: no step here changes the system. If a fix is needed, print the exact command for the user to run themselves and say that it needs their password.

Notes

Every command in this skill is read-only. fastfetch, df, free, sysctl, systemctl --failed, journalctl, ip and cat /proc/... all only read. There is no repair action in the catalog, and this assistant never runs anything as root - it refuses sudo, pkexec, su and doas before they are executed, which is the correct behaviour and not a bug.

df -h sizes are rounded, so a disk at 80 percent with a "5.0G" total really is at 80 percent - do not report it as 80.1. journalctl -p 3 -xb prints the last boot's errors only; a machine that was rebooted since the problem started has already lost the evidence, and saying so is better than reporting a clean boot as healthy.

systemctl --failed is never empty on a machine with a failed unit, but a failed unit is not always the user's problem - a printer unit failing on a machine with no printer is a description of the machine, not a fault. Name the unit, say what it is, and let the user decide whether it matters.

These are the same pages the assistant reads when you ask it something, written out so you can read them without asking. They cover 7 task(s) and 8 of the assistant's procedures, and they ship with the image.

Nothing on this page is fetched from the network, and nothing here leaves the machine.

AstraOS self-test
=================

WHAT IT IS

  The machine describing itself. The unit astraos-smoke.service starts once the
  graphical boot has been reached, waits for the session if it is still loading, prints
  one line per check to the serial console and the journal, holds the desktop for a
  screenshot and powers the machine off. The image's CI boot test (scripts/smoke-boot.sh, run by the smoke-boot
  job of .github/workflows/build-iso.yml) is the same script under automation.

HOW TO RUN IT

  It runs only when the kernel command line contains "astraos.ci=1", so it can never
  surprise a user. To make any AstraOS medium test itself:

    1. at the boot menu, edit the entry (e for GRUB) and add to the kernel line:

           astraos.ci=1 console=ttyS0,115200n8

       the console= part is optional; without it the output is only in the journal.
       Add astraos.phone=1 only when another machine will answer the phone-page
       exercise (scripts/smoke-boot.sh does); without a phone to pair, those checks
       fail after their waits.

    2. boot. The machine reaches the desktop, checks itself, prints ASTRAOS-SMOKE lines
       ending in

           ASTRAOS-SMOKE: RESULT: PASS (n checks, 0 failed)

       holds the desktop for 25 seconds (time to take a photo or a screenshot) and
       powers off.

  Afterwards the full transcript is in the journal:

      journalctl -u astraos-smoke

WHAT IT CHECKS

  * the release identity in /etc/os-release is AstraOS, not the base distribution;
  * LightDM and the Xfce session came up (X socket, xfwm4 running for the live user);
  * every AstraOS package is installed and configured;
  * the hardware and compatibility stack is present: microcode, fwupd, zram, VA-API,
    codecs, Flatpak, Wine, NTFS/exFAT tools, CUPS, Bluetooth, PipeWire;
  * the commands run: the HUD, the assistant, the all-in-one command, the Windows
    bridge, wine, ffmpeg, flatpak;
  * Flatpak knows the Flathub remote; NetworkManager is up, the machine has an
    address, and a real name resolves through DNS;
  * with astraos.phone=1 on the kernel command line: the assistant's page serves on
    the local network, an unpaired guest is refused, a phone that pairs with the
    code the machine prints is served, and the revoked phone is refused again. The
    caller prints the code as "phone-code:" and must answer it.

  * on the live medium, the dashboard (astraos-hud) is started as the live user before
    the screen is held for the capture ("hud-on-screen"), so the caller's picture
    carries the HUD itself, not only the desktop;

  * on the live medium, the assistant measures the machine ("ai-profile"): the command
    reads /proc and /sys as the live user - never as root - and writes the capability
    profile (CPU flags and instruction sets, memory, graphics, audio, free space, and
    the derived AI-readiness rung) beside the assistant's settings. The check requires
    the file the command says it wrote;

  * on the live medium, the offline help centre is present ("help-centre"): the page
    is installed where the "AstraOS Help" launcher opens it, it carries a search box
    and it has topics in it, so the entry in the menu cannot open an empty page;

  * on the live medium, the tools a person reaches for when something is wrong are
    present and run ("recovery-tools"): astraos-doctor and astraos-reset are asked for
    their help text, which proves they are installed, executable and start;

  A line marked "note" is information, not a verdict: the shipped image has no AI model
  installed, so "assistant-status" reporting no model is expected.

FOR BUG REPORTS

  Attach the ASTRAOS-SMOKE lines (or journalctl -u astraos-smoke). They say which
  kernel, CPU and memory the machine has and exactly which check failed, which is the
  difference between a usable hardware report and a guess.
